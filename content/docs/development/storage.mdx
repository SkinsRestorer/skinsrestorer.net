Player storage saves an identifier. Skin storage resolves that identifier to a signed property. The skin applier changes a live profile.

## Persistent change

The [complete plugin example](/docs/development/first-plugin) performs these operations:

1. Resolve input with `SkinStorage.findOrCreateSkinData(input)`. It returns an `Optional<InputDataResult>`.
2. Handle an empty result. Otherwise, unwrap it: `InputDataResult skin = result.get()`.
3. Save `skin.getIdentifier()` with `PlayerStorage.setSkinIdOfPlayer(uuid, identifier)`.
4. Apply `skin.getProperty()` to the live player with the platform's skin applier.

The saved identifier controls future resolution. Applying the already-resolved property avoids another lookup during the immediate refresh.

A storage write and a visual refresh are not one transaction. A player can disconnect after the selection saves. Keep that distinction in error messages.

## Temporary change

`applySkin(player, property)` changes the live appearance without writing the selected identifier. `applySkin(player, identifier)` also changes only the live appearance. Neither overload throws a checked exception.

Use this for previews or temporary effects. On reconnect, normal saved selection and default rules apply again.

## Apply the saved selection

`applySkin(player)` resolves the skin that would apply on join. It can throw `DataRequestException` because resolution can request account data.

To clear a saved selection, call `PlayerStorage.removeSkinIdOfPlayer(uuid)`. Then call `applySkin(player)` to show the skin that the player now resolves to.

## Generate a URL property

Get the MineSkin client with `skinsRestorer.getMineSkinAPI()`. Then call `genSkin(url, SkinVariant.CLASSIC)`. It returns a `MineSkinResponse` and can throw `DataRequestException` and `MineSkinException`. Call `response.getProperty()` to get the generated property.

Applying that property directly is temporary. To store the result as URL skin data, call `SkinStorage.setURLSkinByResponse(url, response)`. This stores the skin data only. It does not change the player's saved selection. For a persistent URL selection, use the skin storage resolution path and save its identifier, as the tutorial does.

`genSkin` also accepts a `File`, `Path`, `BufferedImage`, or `byte[]`. The `File`, `Path`, and `BufferedImage` overloads can also throw `IOException`. The `byte[]` overload does not.

## Read or create data

`PlayerStorage.getSkinForPlayer(uuid, name)` resolves a saved or fallback property and can throw `DataRequestException`.

`SkinStorage.setCustomSkinData(name, property)` stores a named custom entry. Preserve the signed value and signature together.

`PropertyUtils.getSkinTextureUrl(property)` extracts the skin URL. A texture URL alone is not a complete signed property.

## React to skin application

Subscribe to `SkinApplyEvent` through the event bus. The event fires each time the platform skin applier runs on Bukkit, Fabric, NeoForge, Velocity, or BungeeCord. This includes `applySkin` calls from other plugins.

The event at join depends on the platform:

- **Bukkit:** It fires at join only when SkinsRestorer does not use the Paper join listener, for example on Spigot or with `advanced.enablePaperJoinListener: false`.
- **BungeeCord:** It fires during login. At that point, `getPlayer` returns `null`.
- **Velocity, Fabric, and NeoForge:** It does not fire at login. SkinsRestorer sets the login profile directly.

On a proxy network, the proxy fires the event when it changes a skin. The backend fires it again when it applies the skin that the proxy sent.

```java
skinsRestorer.getEventBus().subscribe(this, SkinApplyEvent.class, event -> {
    Player player = event.getPlayer(Player.class);
    // Read or replace event.getProperty(), or cancel the change.
});
```

The event class is `net.skinsrestorer.api.event.SkinApplyEvent`. Pass your plugin instance as the first argument. `setProperty(property)` replaces the skin that SkinsRestorer applies. `setCancelled(true)` stops the change. On Bukkit, the listener runs outside the server thread, so schedule any Bukkit work yourself.

## Failure policy

Keep separate outcomes for missing input, service errors, storage errors, and disconnected players. Do not retry generation in a tight loop.

The API does not automatically apply the command layer's cooldowns, per-skin permissions, or URL restrictions. Your integration must enforce its intended policy.

For a proxy backend, configure [shared API storage](/docs/development/proxy-api) first.
